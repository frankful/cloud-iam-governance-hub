# 第二阶段设计：权限治理与审计证据

**状态：** 提议评审的设计，不代表已承诺实施。

**范围：** 面向非生产试点的 IAM 权限治理与审计证据。LDAP 身份认证和平台组授权另行设计。Terraform apply 流水线集成及 apply 后 AWS 状态比对明确延期。

[English version](./phase2-permissions-audit-design.md)

## 1. 目标

通过可持久追溯的证据，能够回答：

1. 申请了什么权限变更？相对于当前盘点状态，差异是什么？
2. 校验时应用了哪个账号基线和哪些规则？
3. 发现了哪些风险？哪些被阻断、警告、跳过或无法评估？
4. 谁提交、校验、批准/拒绝、发布和关闭了工单？
5. 哪些不可变的申请、审批、校验和 Git 托管平台观察记录属于该工单？

不得宣称静态分析等同于 AWS 授权模拟，不得把 MR 合并说成 Terraform
apply 的证明，也不得仅凭权限技术上已应用，就声称满足了申请人的业务需求。

## 2. 应保留的现有实现

- `iam_baseline` 按账号存储不可变的基线版本；每个账号最多只能启用一个版本。
- 基线采用规范的 `AbstractPolicy` DSL，目前只允许显式 `Allow` 语句、正向
  Action/Resource 模式，以及有限的必需条件（`StringEquals`、
  `StringLike`）。
- 基线匹配刻意采取保守策略；无法证明通配符范围包含关系时，不视为已覆盖。
- `ticket_validation_record` 以追加方式保存校验尝试、请求哈希、基线 ID、
  检查项、跳过项和结果。
- 创建/启用基线和修改 AWS 账号配置时，已有实现会在与数据库变更相同的事务中
  写入审计事件。
- `iam_audit_event` 通过数据库触发器禁止普通更新和删除。已有审计查询及有界导出；
  请求审计中间件在响应后尽力记录，属于补充遥测。
- 当前若干工单路径会跳过逐语句基线检查，包括策略挂载、策略更新、角色更新和回滚。
  工单生命周期变更尚未证明已全面采用与业务状态变更事务耦合的审计约定。

第二阶段应在这些基础上增量扩展，保留已应用的迁移历史，避免重复建设审计日志。

## 3. 权限治理设计

### 3.1 策略层与判定类别

每项权限相关校验都必须区分以下结果：

| 结果 | 含义 |
|---|---|
| `PASS` | 已执行检查，且符合该检查的规则。 |
| `BLOCK` | 存在明确、由策略定义的违规项，阻止提交。 |
| `WARN` | 发现需审核的问题，但按当前配置仍允许提交。 |
| `NOT_APPLICABLE` | 该检查与此工单类型无关。 |
| `SKIPPED` | 检查可能适用，但必要的源数据/配置不可用或被有意禁用；必须附稳定的原因代码。 |
| `ERROR` | 因运行故障或数据完整性问题无法完成检查；不得将其转为通过。 |

为兼容现有数据，持久化的校验尝试保留顶层结果
（`PASSED`、`BLOCKED`、`ERROR`）；每项检查分别携带上述细化结果。
只有在策略允许且所有强制检查均为 `PASS`、`WARN` 或 `NOT_APPLICABLE` 时，
工单才可进入审批。强制检查为 `SKIPPED` 时应阻断，除非该工单类型有明确批准的
替代审核路径。运行错误一律失败关闭。

### 3.2 基线语义

账号基线继续作为按版本管理的最大授权边界，而不是要附加到主体上的 IAM 策略。

- 对新增或扩大的授权，按当前启用的基线进行校验。
- 没有基线时必须明确记录 `NO_BASELINE`。试点期间，只有账号被显式标记为可在
  无基线情况下运行时才可继续提交，否则阻断。该设置不能通过把“无基线”默认为
  “无限制”来替代。
- 仅支持已实现且可测试的 DSL 子集。创建基线时拒绝不支持的 Effect、选择器、
  条件运算符或非字符串条件值。
- 每条校验记录都保存基线版本及不可变 ID；如适用，即使结果为 `NO_BASELINE`
  或 `SKIPPED` 也须记录。
- 通配符匹配采取保守策略。匹配器无法证明已覆盖时，应判定为 `BLOCK`，不能猜测通过。
- 基线变更必须创建新的不可变版本。启用新版本并停用旧版本仍应在同一事务中原子完成并写审计。

### 3.3 按工单类型校验权限差异

不要对所有工单统一采用“目标资源已存在就跳过基线”的规则。应将候选策略文档
规范化为标准策略语句，计算新增/删除/未变化的授权差异，并保留源语句及策略来源。
目标资源已存在，并不意味着变更自动安全。

| 工单类型/操作 | 第二阶段必须采取的处理 |
|---|---|
| `CREATE_ROLE` | 校验所有申请的角色权限、信任策略风险和基线覆盖情况。信任主体/动作属于单独的校验域；基线的 Action/Resource 规则不能授权信任关系。 |
| `ATTACH_USER_POLICY` 挂载 | 从同一账号的资产盘点中，按有记录的快照/版本解析托管策略文档。校验挂载引入的授权是否符合基线及候选风险规则。如果无法解析策略文档/版本或数据已过期，返回带稳定原因的 `SKIPPED`，并要求进入指定人工审核路径；不能仅凭策略名称/ARN 证明权限安全。 |
| `ATTACH_USER_POLICY` 解绑 | 解绑不会新增授权。授权扩张检查记录为 `NOT_APPLICABLE`；仍须校验目标/账号归属以及源工单归属规则。 |
| `UPDATE_MANAGED_POLICY` | 将申请文档与当前盘点到的默认策略版本比较。对新增授权执行基线和风险检查；将移除的授权单独报告为风险降低。如果源文档缺失、过期或无法无损规范化，应阻止提交并要求刷新或明确修复，不能静默跳过。 |
| `UPDATE_GROUP_INLINE_POLICY` | 与托管策略更新采用相同的差异校验，也包括角色内联策略。记录主体类型、策略名称、账号及源快照。组继承可能扩大影响范围；在可获取时展示已知受影响用户/主体作为上下文，但不得声称已完整计算有效授权。 |
| `UPDATE_ROLE` | 使用专门的信任关系风险规则校验信任策略变更，并要求明确的人工审核。如果权限未变，不得声称存在权限授权差异；如果同一操作还修改内联权限，则独立校验该差异。 |
| `ROLLBACK` | 根据目标工单不可变的变更前/后快照，计算实际反向差异。回滚可能重新引入更宽权限，因此须对重新引入的授权执行相同的基线/风险检查。快照缺失或不一致时阻断回滚校验。 |

更新既有策略时，应针对**新增/扩大的授权差异**校验基线，避免因历史授权不符合基线
而冻结所有后续变更。将原本就超出基线的授权单独作为 `WARN`/上下文报告，不得暗示
本次更新会移除这些既有授权。未来也可以要求最终策略整体符合基线，但这需要作为独立的
账号级推广决策。

差异匹配必须确定且保守：

1. 解析源文档和候选文档，并按 DSL 规则规范化语句顺序、Action/Resource 大小写、
   条件及重复语句。
2. 保留语义差异；不得为使比较通过而丢弃条件键、`NotAction`、`NotResource`、
   不支持字段或策略变量。
3. 无法进行精确语义规范化时，以稳定原因将检查标为 `SKIPPED`/`ERROR` 并要求修复；
   不得据此推断没有新增授权。
4. 为界面解释记录稳定的语句索引/来源；幂等身份应使用规范化请求哈希，而不是不稳定的数组位置。

### 3.4 风险策略与例外处理

必须区分强制阻断项和可审核警告：

- 普通审批不可覆盖的强制阻断项包括：请求格式无效/语义不支持、生成器安全保护拒绝的
  通配授权、明确违反基线、不安全的外部信任关系、目标归属缺失或校验数据完整性失败。
- 管理员可配置可审核发现项为阻断或警告。每项发现须包含稳定的 `code`、严重度、
  来源、受影响语句、说明和修复建议。
- 不得加入通用“强制提交”或静默管理员绕过功能。
- 如确有业务例外需求，应单独实现显式、有时限的例外记录，限定账号、主体/资源、
  Action、理由、负责人和到期时间。须由独立授权审批人批准，并在校验证据和审计证据
  中记录例外 ID/版本。例外不能覆盖强制阻断项；过期/撤销的例外不适用于新申请，
  既有不可变工单决定不被改写。

例外管理是可选设计，并非首轮试点的前置条件。试点默认采用严格基线校验，不提供例外绕过。

### 3.5 校验持久化与用户体验

每次校验尝试须包含：

- 工单 ID、尝试序号、请求 SHA-256、校验时间及顶层结果。
- 基线 ID/版本（仅当明确记录 `NO_BASELINE` 时才可为空）。
- 每份策略所用源资产快照的时间戳/版本。
- 各项检查的稳定代码/结果/严重度、简要说明、受影响语句/Action/Resource、
  策略来源，以及跳过/错误原因。
- 最小化的差异摘要（新增/删除/未变化语句数及规范化哈希）。不要在通用日志中复制完整策略文档。
- 校验引擎/规则集版本，以便规则变更后仍可重现旧证据。

提交页面和审批视图应展示：

1. 申请权限；如可获取，同时展示挂载策略展开后的授权。
2. 分别展示新增与移除的授权。
3. 基线版本及具体违规项。
4. 风险发现及对应处理结果。
5. 资产数据新鲜度及所有跳过的检查。
6. 明确提示：该结果是静态策略分析，不是 AWS 授权模拟器，也不是已部署状态的证明。

提交时须基于最新资产和基线重新校验。最终校验记录、审批人快照创建和
`DRAFT` → `APPROVING` 状态转换必须原子完成。任一步失败，工单都保持 `DRAFT`。

### 3.6 权限治理度量

对明确指定的账号和时间窗口，报告：

- 按工单类型及校验结果分类的提交数量。
- 被基线阻断的申请及违反的稳定规则代码。
- 警告/例外数量（如未来启用例外）。
- 按严重度及结果分类的候选风险发现数量。
- 因资产策略缺失/过期而跳过校验的次数。
- 完整且成功的扫描次数，以及最近一次完整成功扫描时间。
- 规范化策略差异中的新增与删除授权数量。

除非对比扫描完整、范围/规则等价且满足明确的新鲜度窗口，否则发现项数量下降不能称为
“风险降低”。拒绝、放弃和未提交草稿须分别统计。

## 4. 审计证据设计

### 4.1 事件模型

继续将 `iam_audit_event` 作为规范的追加式审计表。请求中间件事件保留为补充 HTTP
遥测。新增业务状态转换和安全相关管理操作的领域事件，并使用带版本的元数据结构。

每条事件至少包含：

- 数据库生成的事件 ID 和 UTC 时间戳。
- 稳定的操作者主体；操作者类型（`HUMAN`、`SERVICE`、`SYSTEM`）。对于委托操作，
  同时记录发起的人类用户和服务身份。
- 操作代码、目标资源类型/ID、结果、请求/关联 ID。
- 适用时包含工单编号和账号数据库 ID。
- 元数据结构版本、原因代码，以及不可变校验/基线/执行记录的引用。
- 对内容变更，记录变更前后规范化内容的 SHA-256 哈希和简洁、安全的摘要。权威请求、
  基线/策略仍保存在其领域记录中；默认不要在审计元数据中重复存储秘密或完整策略内容。

绝不记录密码、Bearer/API Token、Authorization 请求头、AWS 凭据、秘密值、原始 LDAP
绑定数据或未脱敏的第三方错误正文。个人数据应限于稳定主体 ID 和必要的显示信息；
审计数据的访问权限应比普通工单读取权限更严格。

### 4.2 必须覆盖的事件

至少记录以下事件：

**权限控制**

- `IAM_BASELINE_CREATED`、`IAM_BASELINE_ENABLED_CHANGED`（已有实现，继续保留）。
- 仅在实现了例外记录时，记录
  `IAM_BASELINE_EXCEPTION_CREATED/APPROVED/REVOKED/EXPIRED`。
- 校验尝试结果，包括基线 ID/版本、校验记录 ID、请求哈希及稳定的检查结果摘要。

**工单生命周期**

- `TICKET_DRAFT_CREATED`、`TICKET_SUBMITTED`、`TICKET_VALIDATION_BLOCKED`、
  `TICKET_APPROVED`、`TICKET_REJECTED`、`TICKET_PUBLISHED`、
  `TICKET_PUBLICATION_FAILED`、`TICKET_MR_STATUS_OBSERVED`、
  `TICKET_CLOSED_APPLIED`、`TICKET_CLOSED_ABANDONED`，以及明确的重试/恢复操作。
- 对审批决定，记录审批人主体、决定、理由/评论引用及不可变审批人快照版本；
  不得覆盖之前的审批决定。
- 对关闭操作，记录发起者/系统来源、关闭原因和评论。
- `MR_STATUS_OBSERVED` 是状态观察，不是 apply/部署事件。在后续流水线集成完成之前，
  当前 `APPLIED` 标签仍须明确其局限。

**身份与授权（与 LDAP 工作线协调）**

- 登录成功/失败、账号禁用/锁定事件，使用非敏感原因代码；不得记录凭据。
- LDAP 同步开始/完成/失败、目录对象计数及水位标记或同步运行 ID；不得导出完整目录记录。
- LDAP 组到平台角色/账号范围/审批人路由映射的创建、变更、停用或删除，并安全地记录变更前后映射 ID。
- Token 签发/撤销、角色分配及账号范围分配。

**证据访问**

- `AUDIT_EVENTS_EXPORTED`（已有实现，继续保留），记录过滤条件、行数、操作者、
  时间窗口及导出摘要/ID。
- 单工单证据包的访问/导出事件，包括证据包版本、涵盖的事件 ID/时间范围、行数及摘要；
  不记录证据包正文。

### 4.3 原子性与故障行为

对仅涉及 PostgreSQL 的变更，业务状态变更和对应审计事件必须在**同一事务**中写入。
若审计插入失败，应回滚业务变更并明确返回错误。该规则适用于工单生命周期、审批决定、
角色/账号范围分配、例外记录和基线变更。

对于外部操作（LDAP 绑定/同步、Git 托管平台发布/状态读取、AWS 资产采集），
PostgreSQL 事务不能涵盖远程副作用：

1. 发起对外可见操作前，持久化操作意图/认领记录和关联 ID。
2. 收到响应后，持久化已脱敏结果和外部稳定引用。
3. 明确规定重试/幂等行为；区分 `UNKNOWN`/超时与远程失败或成功。
4. 结果不确定时，绝不生成看似成功的审计事件。
5. 不得声称尽力而为的中间件日志已使远程操作具备可靠审计能力。

HTTP 中间件仍可用于请求/路由/状态码遥测，但不能替代与业务事务耦合的领域事件。
认证失败可以作为安全事件记录，但不得包含用户提交的凭据；审计写入不可用时，不得因此
授予访问权限或允许未审计的特权变更成功。

### 4.4 工单证据视图与导出

新增按工单范围组织的证据读取模型；从权威数据表汇总引用，而不是复制可变数据：

- 不可变的申请快照和审批人快照。
- 校验尝试、规则集版本、基线版本、检查结果和请求哈希。
- 带操作者、时间戳和评论的批准/拒绝决定。
- Git 提供方/仓库/MR URL、提交及已观察到的 MR/CI 状态。
- 当前平台关闭原因和关闭来源。
- 相关账号同步运行 ID/结果及资产快照时间戳；明确标记为资产刷新，不是逐工单 AWS 状态核验。
- 按顺序排列的领域审计事件及证据完整性清单。

响应/导出必须注明尚未连接部署/apply 流水线结果，且 MR 合并不证明 apply 成功。
不得包含凭据、Token、原始环境配置或无关用户数据。

试点可先采用有界的同步 JSON 导出，并强制限制最大行数和日期范围。增加稳定排序、
导出 ID、结构版本，以及对规范化序列化内容计算的 SHA-256 摘要。导出本身也必须写审计。
如果后续导出规模变大，应改为异步、受控访问且带过期时间的文件，不要取消上限。

### 4.5 保留期限与防篡改

数据库追加式触发器可阻止普通应用账号修改记录，但无法防止数据库所有者或特权 DBA
篡改。不得将其描述为外部不可变保留或符合监管要求的证据存储。

非生产试点期间：

- 在收集大量 LDAP/审计数据前，由系统负责人明确保留期限和访问策略。
- 对审计写入失败和导出活动增加监控。
- 保护备份，并测试审计记录与工单记录的联合恢复。
- 将导出到组织批准的追加式/不可变存储作为独立部署决策进行评估；本设计不指定供应商或保留期限。

## 5. API 与存储变更

优先采用增量变更并复用现有记录：

1. 如果检查项尚未包含等效数据，则为 `ticket_validation_record` 增加规则集版本和源快照引用/哈希。
2. 新增追加式工单生命周期事件行或持久化状态转换时间。建议新增规范化的
   `ticket_lifecycle_event` 表，以工单为键保存稳定事件代码、操作者、发生时间、
   请求 ID 和安全元数据。每行须与工单状态转换在同一事务中插入。用此表度量阶段耗时；
   保留 `iam_audit_event` 作为可搜索的安全/审计账本，并通过事件 ID/关联 ID 链接。
3. 为具备授权的工单读取者新增 `GET /api/v1/tickets/:ticketNo/evidence`；
   权限范围应与现有工单访问控制一致，包括申请人/审批人/管理员范围。
4. 为平台管理员/审批管理员新增有界证据导出路由，并记录导出事件。
5. 只有事件语义稳定后才新增汇总指标；指标必须包含统计窗口、样本数和未知/不可用数量。

避免在审计行中重复存储完整策略内容。复用不可变工单快照、基线版本、校验记录和执行观察记录，
通过稳定 ID 与哈希链接。

## 6. 实施顺序

### 切片 A——定义并测试权限差异规则

- 为每种工单类型及授权扩大/缩小准备测试样例。
- 实现规范化处理和精确的受支持语义。
- 将源状态缺失/过期明确处理为阻断或跳过结果。
- 增加回归测试，覆盖通配符歧义、条件、托管策略挂载、策略更新、仅修改信任关系、
  回滚重新引入授权以及历史遗留的超基线授权。

### 切片 B——持久化校验来源并向用户解释

- 在校验快照中增加源数据新鲜度、规则集版本及新增/删除授权摘要。
- 确保最终校验记录与审批人快照、提交状态转换原子持久化。
- 在提交预览和审批视图中展示稳定的发现项。

### 切片 C——事务性生命周期审计

- 清点所有特权/业务变更路由。
- 为每个成功变更在同一事务中写入一个领域事件。
- 确保失败检查和拒绝尝试有正确记录，不得出现看似成功的事件。
- 增加故障注入测试，证明审计写入失败会回滚业务写入。

### 切片 D——工单证据读取/导出

- 汇总工单、校验、审批、MR、同步及审计引用。
- 增加权限范围测试、脱敏测试、大小/时间边界、规范化摘要和导出自审计。
- 将 apply/部署证据明确标为 `NOT_CONNECTED`。

### 切片 E——试点复盘与度量

- 核实非生产账号以及 LDAP/平台组映射。
- 可靠事件可用后，再对约定时间窗口建立基线。
- 与平台/安全/账号负责人复核阻断/警告授权、跳过项、资产过期、审计完整度和阶段耗时。
- 未使用可比扫描且样本量不足时，不得根据原始计数宣称改进。

## 7. 验收标准

### 权限治理

1. 每种工单类型均有文档说明并测试其校验适用性。
2. 不得因源策略数据缺失、过期、格式错误或语义不支持而让授权差异通过。
3. 新增/扩大的权限必须对照校验证据中记录的准确基线版本进行检查。
4. 移除的权限和原本就超出基线的权限必须与新增权限分开报告。
5. 风险结果使用稳定、机器可读的代码，不能通过通用绕过功能静默降级。
6. 信任策略变更和回滚都必须经过明确校验；回滚不得在未检查权限差异时重新引入授权。
7. 用户和审批人可在审批前看到基线、发现项、源数据新鲜度、跳过检查及分析局限。

### 审计证据

1. 每个成功的工单生命周期变更和特权权限变更都有相关联的领域审计事件。
2. 插入审计事件时发生数据库故障，应回滚对应的 PostgreSQL 业务变更。
3. 审计记录追加写入、无秘密信息、受访问范围保护且排序确定。
4. 工单证据响应链接申请、校验、基线、审批决定、Git 观察、关闭及同步记录，
   且不暗示已完成部署验证。
5. 审计/证据导出有界、已脱敏、计算内容摘要且导出本身也有审计记录。
6. 审计写入故障会明确暴露，不能导致特权变更以成功状态完成。
7. 文档明确说明保留限制；不得声称仅靠数据库追加式机制就构成外部不可变或合规级存储。

## 8. 实施前需要确认的决策

以下为建议默认值；改变持久化语义前应先确认：

1. **试点账号没有基线：** 对生产特征环境建议默认阻断；只有显式启用并记录审计理由
   才允许无基线操作。请确认非生产环境是否也采用严格策略。
2. **源资产过期门槛：** 为策略更新/挂载差异校验选择数据新鲜度窗口。建议超过配置窗口
   即阻断校验，并提供明确的“先同步”路径。
3. **更新时的基线范围：** 本设计只校验新增/扩大的授权，并单独报告历史违规项。
   请确认采用此差异策略，而不是要求最终整个策略都符合基线。
4. **风险发现项：** 确认哪些现有静态规则为强制阻断，哪些可作为警告。生成器对通配授权的安全保护及不支持的语义应始终不可覆盖。
5. **例外：** 建议首轮试点不提供例外绕过；如确有需要，实施前须设计到期机制、独立审批人及不可覆盖的发现项。
6. **审计保留/导出：** 生产使用前确认保留期限、允许导出的操作人员，以及组织批准的不可变存储目标。
