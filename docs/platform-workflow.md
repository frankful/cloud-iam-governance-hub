# 平台标准流程（端到端）

本文是把一台 AWS 账号接入治理、并在其上持续变更的**唯一标准路径**。所有页面、
接口与状态机的设计都服务于这条链路；脱离链路的操作（直接在 AWS 控制台改 IAM、
绕过平台手工改 Terraform）正是漂移检测要抓的对象。

```
注册组织/账号 → 同步库存 → 发布基线 → 建工单 → 审批 → Apply → 关单 → 自动同步 → 漂移检测
                    ↑                                                                    │
                    └──────────────────── 收敛双路（接受现状 / 回滚到声明）────────────────┘
```

## 0. 一句话定位

| 环节 | 性质 | 作用 |
| --- | --- | --- |
| 同步 | 只读 | 摸清 AWS 里现在有什么 |
| 基线 | 写 Git | 把「应该是什么」固化成声明，账号由此**纳管** |
| 工单 | 唯一变更入口 | 任何 IAM 变更都必须留下审批与审计痕迹 |
| 漂移检测 | 兜底 | 抓「绕过平台的改动」并给出两条收敛路径 |

## 1. 注册组织 / 账号

- 页面：账号管理
- 输入：AWS 账号 ID、只读角色 ARN（`read_only_role_arn`）
- 结果：账号进入系统，但**尚未纳管**；漂移页显示「未纳管，不检测」

只读角色只需 IAM 读权限（`iam:Get*`、`iam:List*`）。平台对 AWS 的写操作一律为零，
真正的变更由你自己的 Terraform 流水线执行。

## 2. 同步（只读）

- 页面：同步页（手动触发）；`sync-worker` 后台消费队列
- 内容：用户 / 组 / 角色 / 客户托管策略 / 内联策略 / 组成员关系 / 实例配置档 /
  身份提供商，以及 AWS 托管策略目录
- 产物：`aws_sync_run` 一条运行记录 + 全量库存快照

同步**不改变 AWS 任何状态**，也不产生基线。它的价值是给后续步骤提供「实时事实」。
尚未纳管的账号同步完成后，库存页能看到资源，但漂移页仍是「未纳管」。

## 3. 发布基线（纳管的分界）

- 页面：基线发布（先「预览」出 337 份左右的 `.tf` 文件与问题清单，再「发布」）
- 动作：构建全账号 Terraform 基线 → 推分支 → 开 PR → 人工合并
- 状态机：`PUBLISHING → PUBLISHED / FAILED`；合并后 `MERGED`

发布成功后，`iam_baseline_declaration` 落下当前生效的声明集合。**从此该账号才算
「纳管」**，漂移检测才有判定基准。此前所有比较都无从谈起。

基线发布的验收门禁（导入式接入，详见 README「Adopting an existing account」）：

1. 首个 `terraform plan` 必须是 **import only**：0 改 0 删；
2. 唯一允许的新增是 `aws_iam_group_membership`（该资源类型无法 import）；
3. 合并并 apply 后，第二次 plan 必须 **无变更**——有变更说明同一资源还有别人在管。

## 4. 建工单（唯一的变更入口）

- 页面：新建工单；类型见 README「Ticket types」
- 关键点：**建 IAM 用户本身就是一张 `CREATE_USER` 工单**，不存在「先建用户再建工单」
  这种顺序。绕过工单直接建的用户，会在下一次同步后被判定为「未声明多余资源」。

工单类型覆盖：建角色 / 建策略 / 建用户 / 建组 / 挂策略 / 改角色 / 改策略 /
改组内联策略 / 改组员 / 接管既有内联策略 / 回滚。

## 5. 审批

- 审批人来自账号绑定（`aws_account_approver`），或按策略走 `AUTO`
- 绑定有两个等价入口，写的是同一张表：
  - **用户视角**：「用户与令牌 → 编辑用户 → 可审批的账号」，给一个人授权多个账号
  - **账号视角**：「同步管理 → 账号配置 → 审批人」，给一个账号挑多个审批人
  - 新账号刚接入时用账号视角；日常加人/换人用用户视角，提示里也是先提这个
- 状态：`DRAFT → PENDING → APPROVED / REJECTED`
- 审批通过后进入待发布（`APPROVED`），由 CI 或人工执行 Terraform

审批前平台不生成任何 PR，也不会触碰 AWS。

## 6. Apply 与关单

- CI 执行 `terraform apply` 后回调：`POST /api/v1/tickets/:no/apply-result`
  - `succeeded=true`：关单 + 立即触发一次同步
  - `failed`：只记日志，工单保持原状
- 手动路径：`POST /api/v1/tickets/:no/close`（`reason=APPLIED|ABANDONED`）
- 关联了基线发布时，回执顺带写入 `applied_at / applied_commit_sha / applied_ci_url`
  （首次写入生效，重复回调幂等）

关单触发的同步是**闭环的关键**：库存刷新后，声明与实态才重新对齐。

## 7. 漂移检测（三类来源）

纳管之后，任何「声明与实态不一致」都会变成发现（`iam_drift_finding`）：

| 来源 | 谁发现 | 典型场景 |
| --- | --- | --- |
| `inventory` | 平台同步后比对声明快照 | 有人直接在控制台改了角色信任策略 |
| `ci` | CI 定时 `terraform plan` 上报 | 两次发布之间被手工改动，plan 显示有 diff |
| `publish` | 发布基线时撞到归属冲突 | 同一份 `.tf` 同时被基线和工单/手工作业管理 |

CI 上报接口：`POST /api/v1/aws/drift-reports`，语义是**替换**——本轮没报的
`source=ci` 发现自动关闭，空上报代表干净。该接口与 `apply-result` **并存**：
前者是账号级巡检报告，后者是工单级结果回执。

## 8. 收敛双路

每条 OPEN 的发现只有两个方向，都必须人工确认：

- **接受现状**（`route=acknowledge`）：重发基线，把线上状态写成代码。这是追认，
  不是回滚，会覆盖该账号全部声明文件并开一个基线 PR。
- **回滚到声明**（`route=rollback`）：按声明快照生成一张 `UPDATE_*` 工单草稿，
  仍需审批与 apply 才生效；平台不会直接改 AWS。

接口：`POST /api/v1/drift-findings/:id/remediate`。两个方向的结果都会回到链路：
追认走第 3 步，回滚走第 4 步。

## 9. 常见误区

1. **「同步 = 纳管」**：不对。同步只读摸底，纳管的分界是基线发布成功。
2. **「先建用户再补工单」**：不存在这个顺序，建用户就是工单。
3. **「平台用户 = IAM 用户」**：不是。平台用户（用户管理页）是「谁能登录这个平台」，
   与 AWS 里的 IAM 用户无关，二者由不同的表与流程管理。
4. **「漂移 = 配置错误」**：不是。漂移是「有人绕过了平台」或「基线没跟上」，
   处理方式是追认或回滚，不是简单改配置。
5. **「没检测 = 没问题」**：库空或账号未纳管时，漂移页的「无发现」不代表干净，
   页面顶部会明确标注覆盖范围。
